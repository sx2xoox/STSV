# STSV 코어 설계

STSV 코어는 스트리머 서버에서 운영할 **모든 콘텐츠의 공통 기반**입니다.

## 0. 운영 방식

- 콘텐츠는 **하나씩, 중기적으로** 운영합니다. 시즌마다 가볍게 규칙만 바꾸는 방식이 아닙니다.
- 다음 콘텐츠는 이 공통 플러그인을 기반으로 **새로 제작**합니다. 그래서 공통 플러그인에는 어떤 콘텐츠든 다시 쓰는
  부품(아이템, 가구, 메뉴, 저장소, 기록, 리소스팩 ...)만 두고, 콘텐츠 규칙은 콘텐츠 쪽 플러그인과 콘텐츠 팩에 둡니다.
- 콘텐츠 후보: 경제 서버(일반적인 마인크래프트 경제 서버: 상점, 시장, 거래, 직업 등), 왕국 쟁탈전, 좁혀지는 세계,
  경제 RP, 협동 레이드, 세계관 연재형. 어떤 콘텐츠를 할지는 아직 정하지 않았습니다.
- 콘텐츠를 정하면, 그 콘텐츠가 요구하는 것 중 다른 콘텐츠에도 쓸 만한 것(예: 경제 API)만 공통으로 올립니다.

## 1. 구조

```
[stsv-core]  공통 플러그인 (이 저장소의 plugin/)
  ├─ 모듈 시스템 (StsvModule): 기능 단위로 켜고 끄고, 리로드
  ├─ 저장소 (SQLite 기본 / MySQL): 테이블 버전 관리, 비동기
  ├─ 콘텐츠 팩: 아이템 / 가구 / 레시피 / 3D·2D 모델 / 메뉴 / 칭호 / 보스
  ├─ 메뉴: YAML + 배경 PNG 로 전용 UI (폰트는 자동 생성)
  ├─ 기록: 프로필, 통계, 칭호, 명예의 전당, 콘텐츠 기간
  ├─ 문구: messages.yml (콘텐츠마다 말투를 바꿀 수 있음)
  └─ 리소스팩: 자동 빌드 + 내장 호스팅(기본: 마인크래프트 포트로 함께) + 접속 시 자동 전송

[콘텐츠 플러그인] (예: stsv-economy)
  └─ stsv-core 에 의존. 자기 모듈, 콘텐츠 팩(contents/economy/ 등), 메뉴, 통계만 추가
```

콘텐츠 플러그인에서는 이렇게 사용합니다.
```java
STSVPlugin core = STSVPlugin.get();
core.modules().register(new EconomyModule());                       // 자기 기능
core.db().migrate("economy", List.of(List.of("CREATE TABLE ...")));  // 자기 테이블
core.menus().open(player, "economy:shop", new ShopMenu());          // contents/economy/menus/shop.yml
core.profiles().add(player.getUniqueId(), "money_earned", 1500);     // 기록 (기간별 + 전체)
player.sendMessage(Lang.msg("economy.bought", "item", name));        // messages.yml
```

## 2. 현재 구현됨

| 기능 | 설명 |
|---|---|
| 콘텐츠 팩 | `plugins/STSV/contents/<팩>/`. 첫 실행 때 기본 팩이 자동 설치됨 |
| 커스텀 아이템 | 이름(MiniMessage), 설명, 모델, 최대 스택, 반짝임, 내구도 무한 |
| 3D 모델 | `.bbmodel`을 폴더에 넣으면 자동 변환됨 (큐브, 회전, 발광, 표시 설정) |
| 2D 모델 | `.png`를 넣으면 일반/손에 든 모양 모델이 자동 생성됨 |
| 가구 | 회전 설치, 여러 블록 크기, 충돌(배리어), 클릭 판정, 부수면 회수 |
| 가구 API | 설치/상호작용/파괴 이벤트, `FurnitureBehavior`로 기계 로직 연결 |
| 레시피 | 조합(모양/무형), 화로, 용광로, 훈연기, 모닥불, 석재 절단기 |
| 레시피 보호 | 커스텀 아이템이 바닐라 레시피 재료로 쓰이는 것을 차단 (복사 버그 방지) |
| 리소스팩 | 빌드 → SHA-1 해시 → 내장 웹서버로 배포 → 접속 시 전송. 내용이 같으면 해시도 같음 |
| 관리 | `/관리자 지급, 아이템목록(GUI), 목록, 정보, 보고서, 리로드, 리소스팩` (모든 명령어 한국어). `/관리자 보고서` = TPS·틱 시간·메모리·청크·엔티티 + 콘텐츠 플러그인 보고서 |
| 레시피 편집기 | `/관리자 레시피 생성 <id> <종류>`: 상자 GUI에 재료와 결과물을 넣고 저장하면 바로 등록 (`recipes/editor.yml`) |
| 화로 연료 | 아이템 `fuel: 3200` 또는 `/관리자 연료 설정 <틱>` (`fuels.yml`). 커스텀 아이템은 설정한 경우에만 연료로 탐 |
| 설치 미리보기 | 가구를 들면 설치될 자리에 모델(테두리 발광)과 바닥 범위가 표시됨. 초록 = 설치 가능, 빨강 = 불가. 본인에게만 보임 |
| 앉기 | `furniture.seat` / `seats` 설정. 우클릭으로 앉고, 내리면 가구 앞쪽에 섬 |
| 전용 동작 아이템 | 활, 쇠뇌, 낚싯대, 방패, 검, 갑옷(착용 모습 포함). 바닐라 동작을 그대로 상속 |
| 기본 콘텐츠 자동 업데이트 | 새 jar로 바꾸면 기본 팩이 갱신되고, 빠진 파일은 삭제됨. 직접 수정한 파일은 보존 |
| 음식 | `food:`: 허기, 포만도, 먹는 시간, 동작, 소리, 효과, 반환 아이템, 재사용 대기시간, 추가 회복 |
| 스킨북 | `skin:`: 우클릭으로 창을 열고 도구를 넣으면 겉모습만 교체. 인챈트, 내구도 유지. `/관리자 스킨 해제`로 해제 |
| 치장 + 옷장 | `cosmetic:`: 실제 투구, 방어력, 투구 칸은 그대로 두고 **나가는 패킷만 바꿈**(`CosmeticPackets`, 플레이어별 netty 핸들러). 다른 사람에게는 머리 아이템을 치장으로 보냄. 본인 투구 칸에는 '본인용 아이템'(`CosmeticViews`)을 보냄: 실제 투구의 복사본(이름, 인챈트, 내구도, 툴팁 동일)이고, 아이템 정의가 `display_context`로 갈라져 인벤토리에서는 바닐라 정의 그대로, 머리(`head`)에서만 치장 모델로 그려짐 → 본인 F5와 인벤토리 인형에도 보이고 투구 칸은 실제 투구로 보임. 빈 칸은 바닐라 빈 투구 칸 그림(GUI 스프라이트를 아이템 아틀라스에 추가)과 툴팁 없음. 플레이어가 실제로 받은 리소스팩 기준으로만 적용(새로 만든 팩은 받은 뒤부터, 받기 실패 시 해제). 클라이언트가 스스로 예측한 슬롯(빈 칸 집기, 같은 투구 우클릭 등)은 다음 틱에 본인 엔티티 장비 변경으로 다시 넣음(상자가 열려 있어도 적용됨). 새로 보이는 사람이 투구가 없으면 스폰 묶음에 머리 아이템을 추가. 인챈트된 투구를 쓰면 본인 화면의 치장도 반짝임(클라이언트가 반짝임을 아이템 단위로만 정해서, 인벤토리 아이콘을 그대로 두려면 피할 수 없음). 크리에이티브가 본인용 아이템을 되보내면 원래 아이템으로 복원. 서버 내부가 달라 패킷 처리를 못 하면 다른 사람에게만 보임. 바닐라 머리 아이템 정의 16개는 `tools/assetgen/vanilla_head_items.py`로 클라이언트에서 뽑아 넣음(마인크래프트 버전을 올리면 다시 실행). 옷장 구역에서 `/옷장` → 메뉴. 치장 클릭 = 착용(착용 중이면 벗기, 미보유는 미리보기) → 메뉴가 닫히고 관전 카메라로 마네킹만 보임(몸, 손, 단축바 없음). 웅크리기 = 메뉴, 나가기 버튼 = 나가기. 메뉴가 열려 있는 동안만 크리에이티브 모드: 관전 모드에서는 서버가 메뉴 클릭을 무시하고, 모험 모드에서는 손에 든 아이템과 경험치 바가 보이기 때문. 크리에이티브의 아이템 생성/버리기는 옷장 안에서 막고, 손은 본인 화면에서만 빈손으로 보임. 카메라를 먼저 붙인 뒤 메뉴로 넘어가므로 첫 메뉴부터 단축바가 안 보임 |
| 옷장 메뉴 | 큰 상자(54칸). 위쪽 탭 7개(전체, 부위 5개, 착용 중), 치장 7×4 = 28칸, 넘치면 페이지(이전/다음). 탭을 바꾸면 제목이 바뀌므로 다음 틱에 메뉴를 다시 엶. 칸 배치와 문구는 `menus/wardrobe.yml` (메뉴 프레임워크) |
| 치장 부위 | `cosmetic.slot`: head / above / shoulder / back / tail / pet / trail / kill (pet = `CosmeticPets`: 매 틱 주인 오른쪽 뒤 자리로 16%씩 다가가는 아이템 디스플레이, 걷는 방향을 봄, 10칸 넘게 멀어지면 그 자리에 나타남, `particle` 이 있으면 0.5초마다 하나; trail·kill = `CosmeticEffects`: `particle`(추가 데이터 없는 것, DUST 는 `color`, rainbow = 1.5초에 한 바퀴), trail 은 `height`(발에서 높이, 기본 0.1), `sound`, `lightning`, 나를 볼 수 있는 사람에게만), 부위마다 하나(DB `cosmetic_worn`(player, slot, item). 예전 `cosmetic_equipped` 는 마이그레이션 2에서 head 로 복사). 내용에서 치장의 부위가 바뀌면 다음부터 새 부위에 입혀짐(비어 있을 때) |
| 붙는 치장 (`CosmeticAttachments`) | head 가 아닌 부위 = 착용자마다 아이템 디스플레이 1개(변환 NONE: 모델 (8,8,8) = 기준점). 원점 = 히트박스 꼭대기(클라이언트가 탑승자를 두는 자리, 웅크리면 1.5), 몸 방향(머리 위는 머리 방향)으로 돌림. `cosmetics.anchors` (왼쪽, 위, 앞 블록)로 모델 위치. 웅크리기: 상체가 목을 축으로 0.5rad 숙여지므로 디스플레이를 같은 각도로 숙이고, 꼭대기가 아니라 목을 축으로 돈 것처럼 이동량을 보정(테스트로 확인). 플레이어 크기 속성에 맞춰 커짐. 클라이언트에서만 착용자의 탑승자로 연결(`CosmeticPackets`: 착용자나 디스플레이가 보이게 되는 스폰 묶음, 서버가 보내는 탑승자 패킷에 디스플레이 id 를 더함) → 매 프레임 착용자와 같이 움직임. 서버는 엔티티를 월드에 넣는 순간 주변 플레이어에게 스폰 패킷을 보내므로, 디스플레이는 아무에게도 안 보이게 소환 → 연결 등록 → 보여주기 순서(먼저 등록하지 않으면 연결 없이 도착해서 몸에 안 붙고 따라오기만 함). 안전장치로 2초마다 착용자를 보는 사람에게 연결을 다시 보냄. 서버에서는 탑승자가 아님(탑승자가 있는 플레이어는 순간이동이 실패하므로). 서버 위치는 1블록 이상 벌어질 때만 옮김(추적용), 방향은 매 틱(보간 1틱). 몸 방향은 서버 값(`getBodyYaw`)을 쓰지 않고 클라이언트 계산(LivingEntity.tick)을 그대로 따라 함: 걷는 방향으로, 뒤로 걸으면 앞을 보고, 팔을 휘두르면 머리 쪽으로, 틱마다 30%씩, 머리와 50°(방패 15°) 이내. 서버는 플레이어를 틱하기 직전에 이전 위치를 지금 위치로 맞춰서 플레이어가 걷지 않는 것으로 보고 몸이 머리만 따라가므로, 그 값을 쓰면 옆·대각선으로 걸을 때 날개가 몸과 최대 50° 어긋남. 탈것: 말은 말의 몸 방향, 보트 등은 탈것 방향. 옷장: 미리보기(관전) 중 마네킹을 클릭하면 마네킹 속으로 들어가 관전 상태로 남던 문제 → 카메라 외 관전 시작을 막고 클릭하면 메뉴를 엶. `/관리자 치장 정보` 에 몸에 붙이기 패킷 수(스폰 묶음, 탑승 패킷 보강, 재전송) 패킷 처리를 못 하는 서버에서는 매 틱 순간이동(보간 3틱). 본인에게는 `내 화면에 표시`를 켰을 때만(1인칭에서도 그려짐). 착용자를 못 보는 사람에게는 숨김(5틱마다). 투명·관전·사망 중에는 없앰, 수영·비행·잠자기 자세에서는 아이템만 비움. 리스폰·월드 이동 때 새로 만듦(본인 클라이언트에서는 새 플레이어 엔티티라서) |
| 전용 UI | 폰트 글리프 배경(176×222) + 리소스팩 버튼 아이콘. 그림/설정/글리프 위치가 서로 맞는지 테스트로 확인 |
| 보스 | `bosses/*.yml`: 관절별 3D 모델(디스플레이 엔티티) + 키프레임 애니메이션(부드러운 전환, 머리가 대상을 봄) + 패턴(내려찍기, 돌진, 던지기, 경고 표시 포함) + 페이즈(모델 교체, 강화) + 보스바 + 피해량 순위 + 드롭. 판정은 보이지 않는 철 골렘 |
| 저장소 | `database:` SQLite(파일 하나) 또는 MySQL/MariaDB(여러 서버 공유). 모듈마다 번호 붙은 테이블 변경(`migrate`)을 한 번씩만 적용. 게임 틱을 막지 않도록 DB 전용 스레드에서 실행. 드라이버는 서버가 처음 켤 때 받음 |

## 4. 게임 안에서 아직 확인하지 못한 것

개발 환경에서 서버를 실행할 수 없어서, 실제 26.3 API로 컴파일하고 단위 테스트까지만 통과했습니다. 첫 실행 때 아래를 확인해야 합니다.
